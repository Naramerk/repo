# Remote coder runtime (slice 2): model-generated code tasks on the legacy OpenHands sandbox

Status: design for this slice; implementation lands in the same branch (`lab/remote-coder-runtime`).
Base: `4cab544` (slice 1 merged, PR256); author branch `lab/remote-coder-runtime`.
Live service (verified by the owner): `http://10.32.2.2:8884`, mode `openhands`.

Slice-1 (`docs/remote-coder-design.md`) shipped the typed contract, the durable
submission store and the bounded wire with no runtime attached. This slice wires
execution: an executor task with `tools_hint=['coder']` dispatched in the
AUTOMATIC mode runs against the remote legacy sandbox, and the task CONTENT
(the task text and the expected output descriptors) is generated by the model —
operator `coder_jobs` declarations are not required and are never consulted on
this path. This implements acceptance item 4 of
`docs/plan/autonomous-research-acceptance.md` ("replace operator-authored coder
declarations with generated programs and bounded environments") for the remote
backend only; the local `bwrap`/`local-python` backends keep requiring
`--coder-jobs` (argv is never invented).

## 1. Composition and layers

1. New module `coscientist/tools/coder/remote_runtime.py` holds the runtime:
   `RemoteCoderSettings` (explicit config), `RemoteCoderPolicy` (submit gate),
   `RemoteCoderRuntime.execute` (submit → status → download state machine).
   It imports only slice-1 modules (`remote_contract`, `remote_wire`,
   `remote_store`), `tools.jobs`, `core.execution.artifacts` and the
   `coscientist.mcp.transport.HttpTransport` PROTOCOL (typing only, same shape
   of edge as slice-1's `remote_wire`).
2. The concrete transport stays where the CLI already builds one:
   `tools.mcp_live.open_cli_http_transport()` (the module that already owns the
   CLI live `HttpxTransport` construction). `coscientist.cli` never imports
   `coscientist.mcp` — the layering contract is unchanged.
3. Dispatch stays at the existing coder choke point
   (`cli/run.py` CODER_HINT branch). For `backend="remote-openhands"` the
   branch calls `_dispatch_remote_coder_task` instead of requiring
   `--coder-jobs`; everything after a succeeded outcome (artifact mapping into
   `AgentTaskOutput.outputs`, usage rows, once-per-task dispatch, dep-pending
   skip) is shared with the operator path.
4. The generation step is an agents-layer capability:
   `LlmAgentAdapter.generate_remote_coder_task` — one bounded structured call
   borrowing the required `executor-route` role model (every profile already
   configures it; no new profile keys) and a new versioned prompt
   (`role.remote_coder` v1 in `agents/prompts/roles.py`; no inline prompts).

## 2. Model-generated task content

5. The generation output schema is `RemoteCoderTaskSpec` (agents/schemas.py):
   `task: str` (non-blank) and `outputs: tuple[RemoteCoderOutput, ...]` with
   `name`, `path` (sandbox workspace-relative), `media_type`.
6. The generation payload contains only journaled facts: study request, the
   task draft (key/title/goal/route/depends_on), the task's expected outputs
   (names + media types), and the names of registered study inputs. No CAS
   bytes, no file contents, no prior results are pasted into the prompt.
7. Dispatch validation (fail-closed, typed `CliRefuse`):
   generated output names must be a subset of the task's expected-output names
   and must cover every required expected output; `media_type` must equal the
   declared one; `path` must pass the slice-1 `workspace_path` validator; paths
   are unique across outputs. A schema-invalid generation gets the adapter's
   single bounded repair retry, then refuses.
8. The remote request binds `study_id`, `attempt_id`, `call_id="{attempt}:coder"`,
   the generated `task`, the validated outputs, the study deadline and
   `wait_in_queue=True` (legacy contract). Expected digests/sizes of outputs are
   `None`: nobody can know them before execution, and model-invented digests
   are fabrication.

## 3. Inputs boundary (explicit non-goal of this slice)

9. `inputs=()`: the legacy service fetches inputs by URL, and there is no
   approved remote-reachable publisher for study CAS bytes (slice-1 §52).
   Uploading dep-transfer or study inputs is a follow-up slice behind an
   approved URL publisher. The generation prompt states this explicitly — the
   model is told no input files exist inside the container and the task must
   be fully self-contained — so a data-dependent task fails honestly
   downstream instead of fabricating input bytes.

## 4. JobStore remains the lifecycle authority

10. The JobStore job is submitted and marked running BEFORE the submission
    store reservation and before any POST. Job statuses stay the single
    lifecycle truth: `succeeded` / `failed` / `timed_out` only from this
    runtime; artifacts attach to the job at completion exactly like the local
    backends.
11. `RemoteSubmissionStore` reserves `(study, attempt, call)` identity with the
    request digest (endpoint + policy digest + task + inputs + outputs +
    deadline + wire shape) BEFORE the POST:
    - same identity with a bound remote task → status-only recovery, never a
      resubmit (crash between POST and bind converges on the real task);
    - same identity reserved without a task id → indeterminate, typed refuse
      (never an automatic second POST);
    - changed identity under the same call → `remote_request_identity_conflict`.
12. Only the actual server-returned `task_id` binds, monotonically. A failed
    stop, transport timeout or vanished status never deletes the binding.

## 5. Submit / status / deadline policy

13. The injected policy callback runs before the reservation and before the
    POST (slice-1 §24): it re-checks the identity against the composed config
    (endpoint equality, deadline within the study budget). Denied or unverified
    policy = typed refusal with zero task requests. The policy digest is part
    of the request identity (slice-1 §27).
14. Status polling: single bounded `GET /api/v1/status?task_id` per iteration
    (slice-1 §38: no background scheduler), `poll_interval_s` sleep between
    calls, bounded by the JobStore deadline. Each receipt is stored bounded.
    `s3_uploads` per-input states map to `InputDelivery` observations; with
    `inputs=()` this is a structural no-op that still refuses missing identity.
15. Deadline: the JobStore `wait(until=deadline)` races the poll loop. Deadline
    elapsed → best-effort `POST /api/v1/stop` (receipt kept; the ack is NOT
    termination proof, slice-1 §13/§45) → `CoderOutcome(status="timed_out",
    retryable=True)`. The remote task may still be running remotely; that
    uncertainty is stated in the outcome detail, never hidden. The SAME
    deadline path covers a poll or download exchange that refuses to start
    because the budget elapsed mid-run — a budget refusal is never reported as
    a plain failure. An operator cancellation (`JobCancelled`) is different:
    it returns `failed` / non-retryable (`remote_job_cancelled`) so a retry
    cannot override a deliberate stop.
16. Terminal mapping (terminal remote claim ≠ scientific success):
    - `completed` → download each declared output
      (`GET /api/v1/files/download?task_id&path`), cap bytes, verify declared
      size/sha256 when present (they are `None` in this slice — computed
      digests are recorded), register via `put_sandbox` (producer=sandbox,
      provenance="tool", name=expected output name, `attempt_is_closed`
      enforced) → job `succeeded` with those artifact ids;
    - `completed` carrying `error`/`turn_error` (legacy cooldown/completed
      envelope) → `failed`, non-retryable;
    - `error` / `cancelled` → `failed`, non-retryable;
    - transport uncertainty (timeout, connect failure, oversized/malformed
      response, unknown status value) → `failed` with `retryable=True` where
      the slice-1 error kind is `transport_sent`/`opaque`; never a success.
17. Protocol refusals are typed and complete the job: a 200 answer outside
    the identity schema (`SubmitIdentity`/`TaskIdentity` — e.g. a legacy
    status value outside the RemoteStatus set) is
    `remote_submit_envelope_invalid` / `remote_status_envelope_invalid`, a
    failed download/registration (CAS reject, unreadable artifact) is
    `remote_artifact_register_failed:<ExceptionClass>` — every one of them
    completes the JobStore job as `failed`; the job is never left live.
18. The `CoderOutcome` returned through `invoke_tool(coder)` is the same typed
    contract the local backends return. `succeeded` means "remote claimed
    completion AND declared outputs downloaded into CAS" — it is execution
    evidence only; scientific acceptance stays with the existing checks
    (unchanged in this slice).

## 6. Honest failure and refusals

19. The dispatch converts non-succeeded outcomes into the existing typed
    `CliRefuse` (code 4) with the outcome status/retryable/detail in the
    message — identical to the operator path. No fabricated science, no
    stub outputs.
20. `CoderTool` (write effect) keeps its `invoke_tool` gates: side-effect HITL
    policy, EffectIntended/EffectDone exactly-once, taint deny. The remote
    runtime runs INSIDE `CoderTool.call` via `ctx.extra` injected deps
    (`remote_request`, `remote_runtime`); `CoderTool` refuses a remote request
    on a non-remote backend and vice versa (no mixed execution paths).

## 7. Config surface (no new secrets or keys)

21. `--coder-backend` gains the `remote-openhands` choice. With it,
    `--coder-remote-url` is REQUIRED (no invented endpoint; the known live
    service is recorded here and in run docs, not hard-coded as a default).
    Optional repeated `--coder-remote-header "Name: Value"` feeds auth headers
    if the deployment ever requires them; none are invented. Budgets
    (`RemoteLimits`, receipt caps, poll interval) come from explicit settings
    with validated bounds — the GLM weekly limit surface is untouched.
22. `continue_cmd` keeps its existing gates: it validates the backend through
    the same `resolve_coder_backend`, and its dispatch still requires coder
    job declarations — a resumed study with `remote-openhands` refuses
    honestly (no silent second runtime; parity is a follow-up).

## 8. Verification boundaries

23. Tests use ONLY fake transports (slice-1 §28). The live service may be
    smoke-checked by the operator with a single `GET /api/v1/status` — never a
    POST from tests or agents.
24. No changes to: event schema/versions, checks, criteria catalog, reporting,
    `core/plan`, `bench/lab/glm/checks_catalog.json`, the JobStore contract, or
    the operator `coder_jobs` path for local backends.
25. Remaining known gaps (not claimed): input publishing (§3), `continue_cmd`
    parity (§21), reattachment to a running remote task after process restart
    is status-only recovery (no live log streaming), and no availability/
    isolation claims for the remote service beyond the typed contract.
